# Permit to Work — Task Risk Assessment

A **Permit to Work (PTW)** application with an integrated **task risk
assessment** module. It lets a team raise, assess, approve and track permits for
high‑risk work (hot work, confined space, working at height, electrical
isolation, lifting, excavation, etc.).

The project is split into a separate **frontend**, **backend** and **database**:

```
Permit/
├── frontend/   Static SPA (HTML + CSS + vanilla JS) — talks to the API
└── backend/    REST API (Node + Express) + SQLite database
```

- **frontend/** — the user interface. No build step; it's static files that
  call the backend over HTTP (`fetch`).
- **backend/** — an Express REST API that owns all data and validation.
- **database** — a SQLite database (Node's built‑in `node:sqlite`, no native
  build required) stored at `backend/data/ptw.db`. Permits and their risk‑
  assessment rows are stored in separate, related tables.

## Features

- **Permit register / dashboard** — searchable, filterable table of all permits
  with live status pills, validity window and residual‑risk badge, plus summary
  stat tiles.
- **Permit editor** with four sections:
  1. **Permit details** — title, type, location, applicant/contractor, personnel,
     validity window, work description. Permit numbers are auto‑generated by the
     server (`PTW-<year>-NNN`).
  2. **Hazard identification** — quick‑pick chips for common hazards.
  3. **Task risk assessment** — break the task into steps and score each on a
     **5×5 matrix** (Likelihood × Severity). Capture control measures, then score
     the **residual risk** after controls. Initial/residual risk auto‑calculates
     with colour‑coded bands (Low / Medium / High / Extreme), plus a per‑permit
     summary and a built‑in matrix reference.
  4. **Authorisation & status** — workflow status (Draft → Submitted → Approved →
     Active → Suspended → Closed), issuing authority, PPE, emergency
     arrangements and a sign‑off acknowledgement (required before
     Approved/Active).
- Server‑side validation; an example permit is seeded when the database is empty.

## Risk scoring

`Risk = Likelihood (1–5) × Severity (1–5)`

| Score  | Band     |
|--------|----------|
| 1–4    | Low      |
| 5–9    | Medium   |
| 10–14  | High     |
| 15–25  | Extreme  |

## Running it

You need two processes: the API and a static file server for the frontend.

**1. Start the backend (API + database):**

```bash
cd backend
npm install
npm start            # listens on http://localhost:4000
```

The SQLite database is created automatically at `backend/data/ptw.db` on first
run and seeded with one example permit.

**2. Serve the frontend:**

```bash
cd frontend
python3 -m http.server 5173      # or any static server
# then open http://localhost:5173
```

If your API is not on `http://localhost:4000`, edit `frontend/config.js` and set
`window.PTW_API_BASE` to the API's base URL.

## API

Base URL: `http://localhost:4000/api`

| Method | Path             | Description                  |
|--------|------------------|------------------------------|
| GET    | `/health`        | Health check                 |
| GET    | `/permits`       | List all permits             |
| GET    | `/permits/:id`   | Get one permit               |
| POST   | `/permits`       | Create a permit              |
| PUT    | `/permits/:id`   | Update a permit              |
| DELETE | `/permits/:id`   | Delete a permit              |

See [`backend/README.md`](backend/README.md) for the data model and details.

## Notes & limitations

- No authentication/authorisation is implemented — add an auth layer before any
  real deployment.
- Intended as a practical demo / internal tool, not a certified safety system.
